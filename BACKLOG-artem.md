## 2026-09-17 — Изучение auth-эндпоинтов бэкенда

Прочитан код `identity` и `api-gateway` (без изменений — только исследование, согласно правилу «бэкенд только изучаем»). Ключевые выводы, на которых строится вся auth-логика фронта:

- `POST /auth/register` — `{ username (3-32), password (8-256) }` → `201 { id }`; `409` если username занят.
- `POST /auth/login` — `{ username, password }` → `{ access_token, refresh_token, token_type }`; `401 Invalid credentials`.
- `POST /auth/refresh` — `{ refresh_token }` → новый `access_token`, тот же `refresh_token` (ротации нет).
- `GET /me` (Bearer) → `{ id, username, email, display_name, created_at }` — `email`/`display_name` сейчас всегда `null` (registration их не принимает).
- Токен шлётся как `Authorization: Bearer <access_token>`; gateway сам валидирует JWT (HS256), внутрь сервисов пробрасывает `X-User-Id`.
- Logout-эндпоинта и смены пароля нет — логаут только на клиенте (сброс токенов из стора).
- Только `GET`/`POST` проксируются gateway.

## 2026-09-17 — Разовое исключение: CORS в api-gateway

Обнаружено, что форма логина/регистрации не работает: браузер шлёт preflight `OPTIONS /auth/register`, gateway отвечает `405` (роут заявлен только для `GET`/`POST`, `CORSMiddleware` отсутствовал вовсе) — запрос обрывается ещё до отправки `POST`. Это блокирует любую работу фронта с API, а обойти CORS-preflight с фронта невозможно (ограничение браузера).

**По явному разовому разрешению пользователя** внесена **только эта одна правка** в бэкенд:
- `src/services/api-gateway/app/main.py` — добавлен `CORSMiddleware` (`allow_origins=["*"]`, `allow_methods=["*"]`, `allow_headers=["*"]`, без `allow_credentials`, т.к. авторизация через Bearer-токен, а не cookies).

Больше никаких изменений в `src/services/*` не вносилось и не планируется без отдельного согласования.

## 2026-09-18 — API для настроек (второе разовое исключение на бэкенд)

По итогам обсуждения с командой (см. переписку с бэкенд-разработчиком max) решили не заводить отдельный сервис настроек, а разложить их по сервисам-владельцам сущностей: глобальные настройки — в `identity`, настройки чата — в `communication`, как отдельные независимые модули (не смешивая с `users/`/`chats/`). **По явному разрешению пользователя** реализовано полностью (4 коммита, каждый — по конвенции типов из корневого `README.md`):

- **`feat: add user settings endpoint to identity`** — новый модуль `src/services/identity/app/settings/` (`models.py`, `schemas.py`, `repository.py`, `service.py`, `router.py`), таблица `user_settings` (1:1 с `users` по `user_id`, поля `notifications_enabled`, `accept_calls`). Эндпоинты `GET/PATCH /me/settings`, авторизация через тот же `X-User-Id`, что и `/me`. Миграция `deac91b0f3e7_add_user_settings_table.py`.
- **`feat: add chat settings module to communication`** — аналогичный модуль `src/services/communication/app/settings/`, отдельная таблица `chat_settings` (composite PK `chat_id + user_id`, поле `notifications_muted`) — намеренно **не** колонка в `ChatMember`, чтобы `chats/` остался только про чаты/сообщения. Единственная точка связи двух модулей — вызов `chats_repository.is_user_in_chat()` из `settings/service.py` для проверки членства (403, если чат чужой). Эндпоинты `GET/PATCH /chats/{chat_id}/settings`. Миграция `d5d6506f04e2_add_chat_settings_table.py`.
- **`feat: route /me/settings and PATCH through api-gateway`** — в `api-gateway/app/router.py` два фикса: `resolve_target` теперь маршрутизирует по сегменту `"me"` (а не точному совпадению `path == "me"`), иначе `/me/settings` не находил сервис; в проксирующий роут добавлен метод `PATCH` (был только `GET`/`POST` — иначе `PATCH` ловил бы тот же `405`, что раньше ловил `OPTIONS` до CORS-фикса).
- **`docs: document settings endpoints in identity and communication README`** — обе таблицы HTTP API дополнены новыми строками.

**Проверено end-to-end** через `docker-compose-local.yml` (docker compose up, реальные HTTP-запросы через gateway): регистрация → логин → `GET/PATCH /me/settings` (дефолт создаётся при первом обращении, патч сохраняется) → создание чата между двумя пользователями → `GET/PATCH /chats/{id}/settings` → проверка 403 на чужом чате. Всё отработало корректно.

Заодно поправил свой локальный `docker-compose-local.yml` (не коммитится, gitignore): у `api-gateway` порты нужно объявлять как `ports: !override`, иначе compose **склеивает** список портов с базовым файлом и остаётся конфликтующий `8000:8000` — та же проблема, о которой писала `ksenia` в своём бэклоге.

## 2026-09-18 — Поиск пользователей

Второй фронтендер не мог начинать работу без эндпоинта поиска людей. По той же логике, что и с настройками (см. выше) — не отдельный сервис, а новый маршрут в `identity/app/users/` (данные и так целиком в таблице `users`, отдельный сервис только добавил бы сетевой хоп или дублирование данных).

- **`feat: add user directory search endpoint to identity`** — `POST /users/search`:
  - `tag` — только префикс по `username`, ведущий `@` обрезается, регистр не учитывается;
  - `email`/`phone`/`name` — подстрока в соответствующем поле, регистронезависимо;
  - `query` — тот же поиск подстроки, но сразу по email/phone/name (не по тегу);
  - несколько заданных полей комбинируются через AND; если не задано ни одного — `422`;
  - `limit` — обязательный параметр без дефолта (по требованию пользователя: без зашитого топ-30, пролистывание через увеличение `limit` на каждый следующий запрос — 30, потом 60, потом 90...), сортировка по `username` для стабильной пагинации.
  - Ответ — `UserResponse` (та же схема, что у `/me`/`/users`) без пароля, но **с `id`** — без него результат поиска нельзя было бы использовать (например, для `POST /chats/direct`).
- В модель `User` добавлено поле `phone` (миграция `82ac3e19d573_add_phone_to_users.py`). `email`/`phone`/`display_name` пока всегда `NULL` — эндпоинта их установки ещё нет, так что реально сейчас работает только поиск по тегу; остальное подключится само, как только появится редактирование профиля.
- Тесты (`tests/test_search.py`, 12 штук) заводят пользователей напрямую через новую фикстуру `db_session_maker` в `conftest.py` (обходя HTTP, раз API для email/phone/name ещё нет) — покрыты префикс/подстрока/регистронезависимость/AND-комбинация/лимит-сортировка/422 на пустой фильтр и на отсутствующий `limit`/исключение пароля из ответа. Прогнано локально на одноразовом Postgres в докере (та же конфигурация, что в CI) — 26/26 зелёных, `ruff check .` чист.

Заодно поймал баг в своих же тестовых данных: `username="a4"` короче `min_length=3` — поправил на `a11`/`a12`/`a13`/`a14`.
- **`fix: preserve repeated query params when proxying through api-gateway`** — тот самый баг из комментария ksenia в `useChats.ts` («api-gateway теряет повторяющиеся query-параметры»). Причина: `request.query_params` (Starlette `QueryParams`) передавался в `httpx` как `params=` напрямую; `httpx` трактует его как обычный `Mapping` и вызывает `.items()`, а тот у Starlette схлопывает дубли ключей до последнего значения. Фикс — `request.query_params.multi_items()`, сохраняет все пары. Проверено на живом стеке: `GET /users?ids=A&ids=B` через gateway теперь возвращает обоих, а не только последнего. Воркэраунд ksenia (по одному запросу на `id` в `useChats.ts`) теперь избыточен, но не трогал её файл без отдельного запроса.

Все правки прогнаны через `ruff check .` (чисто) и полный прогон тестов `identity`/`communication` (26 + 12, оба зелёные) на одноразовом Postgres в докере — конфигурация как в CI.

## 2026-09-19 — Nginx как единая точка входа (замена CORS-костыля)

`feat: add nginx reverse proxy as single entry point for the app` — новый сервис `src/services/nginx/` (`nginx.conf`, `Dockerfile`, `README.md`), решает саму причину, из-за которой раньше пришлось городить `CORSMiddleware(allow_origins=["*"])` в `api-gateway`: теперь фронт и API живут под одним origin, и браузер вообще не считает эти запросы кросс-доменными.

- **Маршрутизация**: `/` → `web:3000`, `/api/` → `api-gateway:8000/` (префикс `/api` срезается), `/ws` → `ws-gateway:4333` (с `Upgrade`/`Connection` для WebSocket).
- **Хосты апстримов — через переменные + `resolver 127.0.0.11`**, а не литералами в `proxy_pass`: иначе nginx резолвит имена контейнеров один раз при старте конфига и **падает целиком**, если хоть один сервис (у нас — вечно нестабильный `ws-gateway`, та самая гонка со стримом NATS) ещё не поднялся.
- Две нетривиальные ловушки nginx, на которые сразу же напоролся и поправил:
  1. Переменная в `proxy_pass` отключает автоматическую подстановку пути — заданный после хоста путь идёт **буквально**, без склейки с остатком URI. Пришлось резать префикс `/api` через `rewrite ^/api/(.*)$ /$1 break;` перед `proxy_pass`.
  2. `rewrite ... break` останавливает **все** директивы rewrite-модуля, оставшиеся в блоке — включая `set`. Пришлось переставить `set $api_upstream ...` **перед** `rewrite`, иначе `$api_upstream` оставалась неинициализированной и nginx падал с `500`.
- **`deploy/docker-compose.yml`**: `web` теперь получает `NUXT_PUBLIC_API_BASE=/api`/`NUXT_PUBLIC_WS_BASE=/ws` по умолчанию (относительные пути — работают только за этим nginx); добавлен сервис `nginx`, порт `80`. Локально порт `80` занят чем-то на хосте — в `docker-compose-local.yml` (не коммитится) проброшен на `8081`, и оттуда же убрано переопределение `NUXT_PUBLIC_API_BASE`/`WS_BASE` у `web` (наследует относительные пути из базового файла).
- **`src/web/app/composables/useWs.ts`** — `WebSocket` не умеет резолвить относительные урлы сам, поэтому добавлена `resolveWsBase()`: если `wsBase` начинается с `/`, достраивает `ws://`/`wss://` от `window.location` (схема зависит от `location.protocol`); абсолютные адреса (прямой запуск без nginx) проходят как есть, без изменений в поведении.

**Проверено end-to-end**: полный стек за nginx (порт `8081` локально) — `register`/`login`/`/me`/`PATCH /me/settings` через `/api/...` отработали корректно; настоящая браузерная сессия (Playwright, реальный Chrome) через nginx зафиксировала **0 OPTIONS/preflight-запросов** за весь сценарий регистрация→чаты→настройки — прямое доказательство, что CORS для основного пути пользователя больше не участвует вообще. `CORSMiddleware` в `api-gateway` не убирал — остаётся как фолбэк для прямых обращений в обход nginx (мобильное приложение в будущем, тестовые скрипты и т.п.).

## 2026-09-19 — CORS-мидлварь остаётся, ws-gateway больше не падает на старте

**Вопрос про удаление `CORSMiddleware` из `api-gateway`** — обсудили и решили **не убирать**. Nginx закрывает CORS только для сценария «весь стек в докере через nginx»; повседневная разработка фронта (`npm run dev` в `src/web/` без докера, как описано в `BACKLOG-ksenia.md`) по-прежнему бьёт в `api-gateway` напрямую с другого origin — там CORS всё ещё нужен по-настоящему. Уберём, только если решим, что прямой доступ к `api-gateway` из браузера в обход nginx больше никому не нужен.

**`fix: retry NATS subscribe instead of crashing ws-gateway on startup`** — наконец исправлен старый известный баг: `ws-gateway` подписывается на JetStream-стрим `CHATS`, который создаёт `communication` при своём старте; если `ws-gateway` стартовал раньше — ловил `no stream matches subject` и падал через `log.Fatalf`, роняя весь контейнер из-за обычной гонки при холодном старте, а не реальной поломки.

- `internal/broker/nats.go` — новый `Client.SubscribeToMessagesWithRetry` (15 попыток по 2с, запас 30с), логирует каждую неудачную попытку вместо мгновенного падения.
- `cmd/main.go` — вызывает ретрай-версию вместо одноразовой `SubscribeToMessages`.
- `deploy/docker-compose.yml` — `ws-gateway` теперь ждёт `communication: condition: service_healthy` в `depends_on` (раньше зависел только от `redis`/`nats`) — убирает гонку на уровне оркестрации в обычном случае, ретрай остаётся страховкой на то, что `depends_on` не покрывает (ручной рестарт контейнера и т.п.).

**Проверено принудительным воспроизведением гонки**: остановил `communication`, полностью пересоздал `nats` (чтобы стрима `CHATS` точно не было), перезапустил `ws-gateway` напрямую — увидел в логах попытки 1-9 с `no stream matches subject` **без падения контейнера**, затем поднял `communication` — на 9-й попытке подписка прошла успешно, `ws-gateway` продолжил слушать `:4333`.

## 2026-09-19 — Порт `web` больше не публикуется; диагностика «не работает логин на 8081»

После введения nginx `web` продолжал публиковать свой порт `3000:3000` — по привычке можно было открыть приложение напрямую там, но относительные `NUXT_PUBLIC_API_BASE=/api`/`NUXT_PUBLIC_WS_BASE=/ws` резолвятся от текущего origin, а на `:3000` `/api` обслуживать некому. Запрос попадал в собственный роутер Nuxt-приложения, ловил `302` от нашего же `middleware/auth.global.ts` (как на любой несуществующий путь для неавторизованного пользователя) — снаружи выглядело как молчаливо проваленный логин/регистрация без внятной ошибки.

**`build: stop publishing web's own port now that nginx is the entry point`** — убрал `ports: "3000:3000"` у `web` в `docker-compose.yml` (и в локальном оверрайде). Теперь у `web` вообще нет прямого входа с хоста — единственный путь внутрь всего стека — через `nginx`.

Отдельно проверил жалобу «и на `8081` тоже не работает» — пересобрал `web`+`nginx` с нуля и прогнал реальный браузерный сценарий (Playwright, настоящий Chrome) через `localhost:8081`: регистрация → логин → `/me` → `/chats` — всё `200`/`201`, редирект на экран чатов. На тот момент решил, что проблема не воспроизвелась (закэшированное состояние). **Ошибся** — пользователь прислал скриншот консоли браузера: запросы реально уходили на абсолютный `http://localhost:8000/auth/login` вместо `/api/auth/login`, и это било в CORS (порт `8000` на хосте не проброшен локально — только `8080`).

Настоящая причина: `docker exec web env` показал, что внутри контейнера `NUXT_PUBLIC_API_BASE` вообще не задана. Когда я убирал `ports: "3000:3000"` у `web` в локальном оверрайде, заодно (ещё до этого) убрал оттуда и `environment:`-блок, положившись на то, что он подхватится из базового `docker-compose.yml` при объединении файлов. Это работает, только если оба файла запускать **вместе** (`-f docker-compose.yml -f docker-compose-local.yml`); если когда-либо (кем угодно) локальный файл поднимается отдельно — `environment` для `web` там просто отсутствует, и Nuxt тихо откатывается на захардкоженный дефолт `http://localhost:8000` из `nuxt.config.ts`. Внешне это выглядит как «не работает логин» без единой явной причины в UI.

Исправил — вернул явный `environment: NUXT_PUBLIC_API_BASE: /api / NUXT_PUBLIC_WS_BASE: /ws` в `docker-compose-local.yml` (дублирует базовый дефолт, но теперь оверрайд самодостаточен). Перепроверил тем же браузерным сценарием — `apiBase`/`wsBase` в `window.__NUXT__.config` теперь корректно `/api`/`/ws`, полный флоу регистрация→логин→`/me`→`/chats` снова зелёный. Предупреждение об этой ловушке добавил в `src/services/nginx/README.md`, чтобы не наступить снова с другим оверрайдом.

## 2026-09-20 — Разбор масштабирования + healthcheck для NATS

**Обсуждение масштабирования** (без изменений кода) — коллега прислал доводы про stateless-архитектуру, WebSocket, presence, БД как бутылочное горлышко. Сверил с реальным кодом репозитория:

- `identity`/`communication`/`api-gateway` — уже полностью stateless (никакого in-memory состояния между запросами), плюс JWT вместо серверных сессий — даже сильнее требования «сессии в Redis».
- `ws-gateway` — WebSocket-шина между инстансами уже фактически реализована через NATS: `c.js.Subscribe(subject, handler)` без durable-имени/queue-группы → каждый инстанс получает копию каждого события и сам решает, доставлять ли локально подключённому юзеру. Ровно паттерн «шина + локальная фильтрация», который предлагал коллега — просто на NATS, а не на отдельном Redis Pub/Sub.
- Presence — уже в Redis (`internal/presence/redis.go`), не в памяти инстанса.
- Единственный реально непокрытый пункт — БД: один Postgres без реплик/шардирования, будет первым бутылочным горлышком при росте до сотни сервисов. Плюс SPOF на уровне инфры (один NATS, один Redis, один Postgres без кластеризации) — отдельная ось от «stateless-код».

**`feat: добавить healthcheck для NATS и зависимость communication от него`** — по комментарию коллеги к ревью `nats.go`. `nats` теперь стартует с `-m 8222` (monitoring-порт) и healthcheck на `/healthz`; `communication` ждёт `nats: condition: service_healthy` в `depends_on` вместо неявного предположения, что NATS уже готов к моменту своего собственного старта (communication создаёт JetStream-стрим `CHATS` в `lifespan`, до этого — race).

**Попутно найден и исправлен реальный баг в `docker-compose-local.yml`** (гитигнорится, но чуть не привёл к тихой поломке): файл дублировал **целые блоки** сервисов, скопированные из базового `docker-compose.yml`, вместо того чтобы переопределять только нужные ключи (порты, env). Поскольку `command`/`depends_on` при слиянии compose-файлов **полностью заменяются**, а не сливаются по вложенным ключам — устаревшие копии в оверрайде тихо съедали свежие изменения из базового файла (новый `-m 8222` у `nats`, новую зависимость `communication`→`nats`, ранее добавленную `ws-gateway`→`communication`). Переписал `docker-compose-local.yml` на минимальные, точечные оверрайды (только `ports`/`environment`, без копирования всего сервиса) — теперь слияние с базовым файлом действительно подтягивает актуальные `command`/`depends_on`, а не версию на момент копирования. Проверено холодным стартом всего стека — `nats` доходит до `healthy` раньше `communication`, полный флоу регистрации через nginx зелёный.
