# Nginx

Единая точка входа для всей системы. Отдаёт фронтенд и проксирует API/WebSocket под одним origin, поэтому браузеру для запросов к бэкенду больше не нужен CORS — они same-origin.

## Структура

```text
nginx.conf           реальная конфигурация, гитигнорится — своя на каждом сервере
nginx.conf.example    шаблон-заготовка (в репозитории): скопировать и настроить под себя
Dockerfile            образ на базе nginx:1.27-alpine
```

`nginx.conf` — тот же паттерн, что и `.env` у остальных сервисов: настраивается локально (домен, сертификат — это специфично для конкретного сервера) и не хранится в git, в репозитории только пример. **На новом окружении перед первым `docker compose up --build` нужно вручную создать `nginx.conf`** — скопировать `nginx.conf.example` (для прод-домена с HTTPS, см. ниже) или взять локальный `http`-вариант (см. предыдущую версию файла в истории git, если нужен образец для localhost) — без него `Dockerfile` упадёт на `COPY nginx.conf ...`, файла просто не будет.

`client_max_body_size 0` (без ограничения) в обоих файлах — намеренно: лимит на размер загружаемого файла задаёт `file-orchestrator` (`MAX_UPLOAD_SIZE_BYTES` + физическое место на диске), nginx не должен резать раньше него отдельным, никак не связанным числом.

## Маршрутизация

| Путь | Куда | Назначение |
|---|---|---|
| `/api/` | `api-gateway:8000/` (префикс `/api` срезается) | REST API |
| `/ws` | `ws-gateway:4333` (с `Upgrade`/`Connection` для WebSocket) | Реалтайм-доставка |
| `/` | `web:3000` | Фронтенд (Nuxt) |

## Как это связано с фронтом

`src/web` должен получать `NUXT_PUBLIC_API_BASE=/api` и `NUXT_PUBLIC_WS_BASE=/ws` (относительные пути), когда работает за этим nginx — тогда запросы идут на тот же origin, что и сама страница, и `CORSMiddleware` в `api-gateway` фактически не участвует в этом пути (остаётся только как фолбэк для клиентов, которые ходят в `api-gateway` напрямую, в обход nginx).

Приложение целиком открывается по адресу самого nginx (`http://localhost/` при локальном запуске) — не через прямой порт `web`, поэтому в `deploy/docker-compose.yml` `web` вообще не публикует свой порт наружу.

**Частая ловушка с локальными оверрайдами (`docker-compose-local.yml`, гитигнорится):** если в оверрайде переопределить у `web` любой ключ (например, `ports`), не продублировав при этом `environment: NUXT_PUBLIC_API_BASE: /api` / `NUXT_PUBLIC_WS_BASE: /ws` — итоговый сервис соберётся из base+override файлов корректно, но если оверрайд-файл когда-нибудь запустят **отдельно, без базового** (`docker compose -f docker-compose-local.yml up`, без `-f docker-compose.yml`), `environment` в `web` там будет попросту отсутствовать, и Nuxt тихо откатится на захардкоженный дефолт `http://localhost:8000` из `nuxt.config.ts`. Выглядит это как «не работает логин/регистрация» без единой явной ошибки — реальная причина видна только через `docker exec web env` или `curl .../login | grep __NUXT__.config`. Поэтому каждый оверрайд `web` должен сам явно задавать `NUXT_PUBLIC_API_BASE`/`NUXT_PUBLIC_WS_BASE`, а не полагаться на наследование от базового файла.

## Запуск

Через `docker compose up --build` из `deploy/` — сервис поднимается вместе с остальными, слушает `80` порт контейнера.

## Прод-деплой с доменом и HTTPS

Для реального домена — взять `nginx.conf.example` за основу своего локального `nginx.conf`: там пошагово расписано, что поменять (домен в `server_name`, пути к сертификату/ключу) и как получить сертификат Let's Encrypt через certbot без даунтайма. Домену достаточно указать A-запись на IP сервера и открыть `80`/`443` наружу — сам код приложения (фронт, api-gateway и т.д.) от домена не зависит, всё продолжает работать через относительные пути (`/api`, `/ws`). Для локального запуска без домена — свой `nginx.conf` с `server_name _;` и чистым HTTP (без TLS-блока).
