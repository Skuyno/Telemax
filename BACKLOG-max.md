## 2026-09-14 — Внутренний эндпоинт для поиска собеседников по чатам

Коммит `40c9b33` — `feat: add internal endpoint for chat peer lookup`.

Добавлен служебный (internal) роут в сервисе `communication` для получения списка пользователей, с которыми у заданного пользователя есть хотя бы один общий чат. Предназначен для service-to-service вызовов внутри docker-сети (по аналогии с `identity`'s `/internal/users/{user_id}`), наружу через `api-gateway` не проксируется.

- **`src/services/communication/app/internal/router.py`** (новый файл) — `GET /internal/users/{user_id}/chat-peers` → `ChatPeersResponse`.
- **`src/services/communication/app/internal/schemas.py`** (новый файл) — `ChatPeersResponse { user_ids: list[UUID] }`.
- **`src/services/communication/app/internal/__init__.py`** (новый, пустой) — обозначает пакет `internal`.
- **`src/services/communication/app/chats/repository.py`** — новая функция `list_chat_peer_ids(db, user_id)`: через `ChatMember` находит все `chat_id`, где состоит `user_id`, затем возвращает `DISTINCT user_id` остальных участников этих чатов (отсортировано по id).
- **`src/services/communication/app/chats/service.py`** — тонкая обёртка `list_chat_peer_ids`, пробрасывающая вызов в repository-слой (по аналогии с остальными методами сервиса).
- **`src/services/communication/app/main.py`** — зарегистрирован `internal_router` (`app.include_router(internal_router)`), рядом с `chats_router`/`health_router`.

### Как использовать / зачем

Позволяет любому internal-потребителю (например, будущей логике подсказок «с кем чаще всего переписываетесь» или предзагрузке профилей собеседников) одним запросом получить id всех, с кем у пользователя есть общий чат, не гоняя `GET /chats` + перебор участников на клиенте.

### На заметку при мёрже в `dev`

- Эндпоинт не публичный — `api-gateway` его не роутит (в `resolve_target` учтены только `auth`, `users`, `me`, `chats`), так и задумано, менять не нужно если не требуется внешний доступ.
- Стоит свериться, что имя `ChatMember` и путь импорта не разъехались с тем, что сейчас в `dev` после чужих мёржей (страница чатов от `ksenia` активно трогала соседние файлы `chats/*` на фронте, но не на бэкенде — конфликтов по этому файлу на бэкенде быть не должно).

## 2026-09-20 — Realtime presence в WS Gateway

Коммит `c706cf3` — `feat: add realtime presence updates to ws-gateway`.

WS Gateway теперь не только хранит presence в Redis, но и сообщает клиентам актуальные статусы пользователей, с которыми у них есть общие чаты.

- Добавлен HTTP-клиент Communication Service для вызова внутреннего эндпоинта `GET /internal/users/{user_id}/chat-peers`.
- В конфигурацию WS Gateway добавлена переменная `COMMUNICATION_URL`.
- Redis-клиент получил пакетное чтение статусов через `MGET`.
- При подключении клиент получает начальный snapshot статусов своих собеседников в событиях `presence`.
- Событие `online` рассылается только при первом активном соединении пользователя, а `offline` — после закрытия последнего; закрытие одной из нескольких вкладок не сбрасывает статус.
- Добавлена входящая WS-команда `{"type":"presence.sync"}` для повторной синхронизации после создания нового чата. Частота команды ограничена одним запросом в пять секунд.
- Presence рассылается только пользователям, имеющим общий чат с изменившим статус пользователем.
- Изменения объединены с актуальной диспетчеризацией NATS-событий из `dev`; внешний контракт `message.created` не изменился.

Проверки после объединения с `dev`: `go test ./...` и `go vet ./...` проходят.

### На заметку для Ксюши и её frontend-агента

Backend-часть presence готова, но без обработки на frontend статус визуально не появится. При следующей работе с интерфейсом чатов нужно:

- обработать входящее WS-событие `{"type":"presence","data":{"user_id":"...","status":"online|offline"}}` и хранить последний статус по `user_id`;
- сохранить `user_id` собеседника рядом с данными личного чата, чтобы связать событие presence с нужным элементом списка и заголовком диалога;
- после успешного создания нового личного чата отправить в уже открытый WebSocket команду `{"type":"presence.sync"}` — сервер сам определит доступных собеседников, передавать UUID в команде не нужно;
- учитывать, что команда `presence.sync` ограничена на сервере одним запросом в пять секунд.

Текущая backend-рассылка переходов online/offline рассчитана на один экземпляр WS Gateway. Это ограничение серверной части; для горизонтального масштабирования потребуется межинстансовая доставка presence-событий.

## 2026-10-02 — Групповые чаты: контракт и тесты

Backend поддерживает создание группы (в том числе только с владельцем), общий список direct/group, добавление и удаление участников, выход и переименование. Управление — у `owner`, самостоятельный выход — у `member`; передача владения пока отсутствует. Изменения публикуют `chat.sync_required`, WS Gateway доставляет сигнал всем подключениям получателей. Добавлены тесты API, прав доступа, повторных операций и WS-конверта/fan-out; Go-проверки подключены к CI.

### На заметку для Ксюши и её frontend-агента

Обработчика группового sync на фронтенде пока нет. Контракт:

```json
{"type":"chat.sync_required","data":{"chat_id":"<uuid>","reason":"members_added"}}
```

- Причины: `created`, `updated`, `members_added`, `member_removed`. После сигнала обновить `GET /chats` (единый список; поля `type`, `title`, `last_message`, `unread_count`). Событие не содержит название или новый состав.
- Если чат остался доступен, обновить его участников через `GET /chats/{id}/members`, когда они нужны интерфейсу. Если исчез — закрыть открытый чат и убрать его локальные данные; не запрашивать историю удалённой группы.
- Сигнал получают также добавленные и удалённые участники. Дубли допустимы, обновления стоит объединять; сообщение в истории по-прежнему объединять по серверному `id`/WS `message_id`.
- На каждом reconnect перечитывать список чатов и доступную историю: NATS-публикация выполняется после commit, гарантированного восстановления события пока нет.
- После изменения состава можно отправить `{"type":"presence.sync"}` (серверный cooldown — пять секунд), чтобы обновить статусы новых собеседников.
- Отдельно нужны интерфейс создания группы и управление участниками/названием с учётом роли. Эта запись не означает, что групповой UI уже готов.
